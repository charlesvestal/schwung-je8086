# The Remote UI

`src/remote/web_ui.html` is the JE-8086's browser panel. Schwung Manager looks
for a `web_ui.html` beside a module's `module.json`, and when the module is
loaded in a shadow slot it shows that page in a sandboxed iframe on
`http://move.local:7700/remote-ui` instead of the knob-and-slider view it would
otherwise generate. The page also opens on its own (the manager's pop-out), on a
phone or a laptop, and drives the same slot.

The design brief was two sentences: world class, and faithful to the JP-8000.
So the page is the front panel -- the manual's sections 1 to 22 in the manual's
order, waveform selectors as button-and-LED columns, the envelopes as faders,
Panel Select and the amber display -- laid out on a grid that reflows down to a
phone, with the things a screen can do that a panel cannot: a live scope for
every envelope, the filter and LFO 1, the other part's value as a tick on every
knob, and a searchable list of every preset in every bank.

## The tabs

Presets · Panel · Osc · Filter & Amp · LFO & Mod · FX · Play & Arp · System,
under a header (display, Mode, Panel Select, Prev/Next) that never moves.
**Panel** is the whole front panel in the hardware's layout, for a wide screen.
The five focused tabs are the SAME sections -- the split follows the panel's own
groupings -- shown fewer at a time with taller scopes and larger knobs, which is
what a phone needs. **Presets** gives the bank/number matrix the full height.
**System** is a view, not the module's mode: switching to it never sends
`mode=System`, so the remote cannot flip the device's own screen into its system
pages; the header's Mode buttons are Patch and Performance only. The chosen tab
is remembered per browser. `TABS` in `jp-model.js` is the split, and the model
test asserts every section sits on exactly one focused tab.

## Files

| file | what |
|------|------|
| `src/remote/web_ui.html` | entry point; loads the manager's bridge script and the three assets |
| `src/remote/assets/style.css` | the panel's one visual world (see below) |
| `src/remote/assets/jp-model.js` | pure: temp decode/encode, display text, THE PANEL definition |
| `src/remote/assets/app.js` | DOM: widgets, bridge, LCD, browser, scopes |
| `src/remote/assets/params.js` | GENERATED by `src/tools/gen_remote_params.py` from `jp8000_params.h` |
| `src/remote/dev/mock-bridge.js` | a stand-in manager for looking at the page with no device; never shipped |
| `src/tools/remote_preview.py` | bundles page + mock into one HTML file |
| `tests/remote/model_test.mjs` | `node` test: byte layout, panel coverage, round trips |

`build.sh` regenerates `params.js`, copies `web_ui.html` and `assets/` into
`dist/jp8000/`; `install.sh` ships them; CI fails if the committed `params.js`
is stale or the model test fails.

## How values reach the page

**Everything on the panel is decoded from `temp`.** The manager seeds a slot's
browser clients from the module's `state` blob, flattened one JSON field per
key, and it does this INSTEAD of reading `chain_params` one by one when `state`
parses. Ours parses, so what a client receives is `synth:temp` (1056 hex
characters: the whole 528-byte temp performance exactly as `state_get` writes
it) and `synth:sys`, plus the integers `mode`, `part`, `bank`, `patch`,
`perf_bank`, `performance`, `buffer_ms`. Never `synth:cutoff`. So the page
carries the same address table the plugin compiled in -- `gen_remote_params.py`
reads it out of `jp8000_params.h`, on purpose from the HEADER and not from
gearmulator's JSON, so page and plugin cannot disagree about where a byte lives
-- and reads every parameter out of the image. One string, 180 values, atomic.

Single values DO arrive when something moves on the Move (the shim's notify ring
pushes `synth:<key>`), and the page applies those to its copy of the image for
the current edit part.

**Writes** go through `schwungRemote.setParam("synth:<key>", value)` with the
displayed value (the plugin's `atoi` path); the page writes its own image first
so the knob does not wait for the round trip, throttles drags to ~30 Hz, and
marks the cell pending until the next dump. The manager re-reads `state` 250 ms
after the last write of a gesture and pushes it to every client, which is what
confirms an edit and what keeps a second phone in step.

**A preset moved on the device** arrives as `synth:patch` (or `performance`,
`bank`, `perf_bank`, `mode`, `part`) with no new `temp` beside it -- the notify
ring carries indices, and the manager only re-pushes whole state for a key
literally named `preset`. The page then writes `temp_refresh=1`: a plugin key
that asks the firmware to dump the temp performance back, and a write, so the
manager re-reads state 250 ms later and pushes it. `Re-read` in the header does
the same by hand.

**NEVER call `schwungRemote.resubscribe()` from a slot page.** It makes the
manager re-send the slot's hierarchy, and the manager's page answers a
hierarchy message with `renderSlot()`, which empties the slot's DOM -- iframe
included -- and reloads this page from scratch. The first device build did that
after every preset or bank selection, to confirm the load, and was reported as
"the whole app refreshes when I change a preset". The `temp_refresh` nudge
above is the whole replacement.

**The browser is the hardware's matrix.** The JP-8000 picks a sound with BANK
1-8 and NUMBER 1-8 buttons, 64 to a bank, spelled `A11`..`A88` on its display.
The browser keeps that: eight cells to a row, the code on every cell, banks as a
pane beside it. Around it, what a screen can add: one search across every bank
(by name, code or number), filter chips made from the names' own two- or
three-letter prefixes when a library uses them (`LD`, `PD`, `BS`...), favourites
kept in the browser's localStorage, a random pick from whatever is listed,
arrow-key movement through the matrix and `/` to search. The highlighted cell
is the module's ROW; the header adds "sounding: ..." whenever the temp image's
name disagrees with it (a patch loaded into the other part, say), because the
row and the sound are two different facts and the device UI once conflated them.

**Real libraries are folders of one-performance files.** The first device test
showed 60 performance banks of one preset each, most with a BLANK name in the
file, and chips reading HAM / THE / JP from names that were never tags. So: a
row with no name shows its file's name (the only honest label there is); chips
appear only when uppercase 2-3 letter prefixes occur three times or more AND
cover a sixth of the presets; codes like `A23` are used only in banks of more
than eight; the catalog carries each bank's `folder` and the banks pane groups
by it; and an **All banks** entry lists everything, with single-preset files
grouped under their folder. **A load is confirmed by a STABLE image, not by name.** The manager re-reads
state 250 ms after a write, before the firmware has clocked in a performance, so
the first dump after a selection can still be the old sound. Measured on the
device with `tools`-style socket probes: the performance NAME lands ~300 ms
after the selection, the two patches, arpeggiator and effects up to ~700 ms
later. A page that stopped at the matching name kept the previous sound's arp
and FX on screen -- the first device bug report. So the page keeps nudging on a
widening schedule (0.6, 1.2, 2, 3.2, 5 s) until the name matches AND two
consecutive dumps are byte-identical, then stops. The same confirmation runs
for a preset changed on the Move, with the expected name taken from the catalog. **The grid updates in place**:
rebuilding it on every dump was a visible flicker on each preset switch.

**The preset list comes from a file.** The bridge cannot ask for
`synth:patch_name:N`; `getParam` answers from the parent's cache. What the
manager does serve is any file under the module folder, so the child writes
`banks_index.json` there once the scan is done (`child_write_catalog`, temp name
plus rename) and the page fetches
`/api/remote-ui/module-assets/jp8000/banks_index.json`. Row order is the shm
order, so an index picked out of that file is the index the page writes to
`patch`/`performance`; the `! N files ignored` row is in it with no presets.
Without the file (an older dsp.so) the browser degrades to prev/next with the
current name.

## What the page does NOT do

- Play notes. A chain slot has no note path from the browser; the pads and a
  controller do that.
- Show the ribbon or velocity depths as anything but knobs. They are modulation
  depths, not values, so they get no scope (docs in `gen_params.py`).
- Report `mode` as anything but the module's own UI fact. Patch/Performance
  choose which browser is shown; the firmware has no such switch.

## The visual world

One theme, deliberately: a JP-8000 is a dark gunmetal panel with white legends,
red LEDs and an amber display, and it is the same object in a bright room. The
page paints its own ground (the manager's `#0c0c0e`) so it sits flush in the
manager and holds on any host. Tokens live at the top of `style.css`.

Type: Plus Jakarta Sans for legends (600/700, uppercase, tracked -- the panel's
legend voice) and IBM Plex Mono for the display and every number. Both are the
manager's own faces, loaded same-origin from `/static/fonts`, so the page needs
no internet; the preview bundle takes the same faces from Google Fonts.

The layout is the panel's: top strip LFO 1 / OSC Common / Arpeggiator; main row
OSC 1 / OSC 2 / Filter / Amp; below it Key & Panel / Tone / Chorus / Delay; the
left block Controller / LFO 2 / Keyboard; and the two Parts plus the external
trigger, which the panel keeps in the LCD. Widgets follow the panel too:
waveforms and types are LED columns, envelopes are faders, the long lists the
hardware scrolls through on the LCD (beat pattern, chorus and delay type, sync)
are selects. LFO 2 has ONE depth knob that follows Depth Select, as the panel
has, with the three bytes behind it. The System area is a mode you enter
(SHIFT/EXIT on the hardware), not a page of the performance, so it replaces the
panel while selected.

**The widths that matter are the Manager's, not the screen's.** The Manager's
page column is capped at 1200px and pads twice on the way down, so the iframe is
~1084px wide on a Mac, ~908px on an iPad in landscape and ~700px in portrait;
only a popped-out window is wider. Three layouts: above 1250px the hardware rows
with the wide column shares (`COLS` in app.js, capped at 1560px and centred so a
1920px pop-out is not a field of giant scopes); 1000-1250px the same rows with
the medium shares (`COLS_MD`), which give OSC 1 and the Filter more room; below
1000px the rows dissolve and the sixteen sections flow two to a line in panel
order -- sixteen is even, so nothing is orphaned. Verified by rendering the page
inside iframes of exactly those widths; a bare headless Chrome window will not go
under 500px and lays the page out at 500 whatever it is told.

**A canvas is never a grid item.** Each display is a canvas positioned
absolutely inside a `.vizbox` that owns the size. A canvas's intrinsic size is
its backing store -- CSS size times devicePixelRatio, which `ctx2d` sets on
every redraw -- and a canvas that IS the grid item feeds that back into an
`auto` track: on a Retina screen the track grows, the canvas is redrawn larger,
the track grows again. Chrome breaks the loop after a frame (and still ended up
640px taller than the content); Safari lets it run and the displays climbed
without end, which is how it was reported. Out of the flow, the canvas cannot
size anything. The same class of bug once inflated the page's WIDTH.

**No gaps, by construction.** Sections in a row are stretched to the tallest,
and every section is a grid of three rows: a `max-content` header, then the
display and the controls as two `auto` tracks. The grid stretches auto tracks
equally, so whatever height a row leaves a shorter section is shared between a
taller scope and roomier controls (the cells spread evenly). Two things this is
NOT, both tried: `fr` tracks, which inflate a section's intrinsic height in an
indefinite row and make the whole row taller than its content; and fractions
summing below 1, which hand the remainder to the header track so the title
sinks. Every section has a display for the same reason -- a section without one
has nothing to grow.

The controls are drawn, not photographed: knobs are SVG with a machined cap, a
recessed well, a tick scale, a glowing value arc and a centre detent on bipolar
ones, and the pointer eases when a value arrives from the device (not while your
finger is on it, and not under `prefers-reduced-motion`). Waveform and filter
selectors carry the panel's printed glyphs. The scopes are small phosphor
displays -- grid, glowing trace, area fill, a dashed cutoff or gate marker -- and
the LFO 1 scope runs at the LFO's rate while its tab is showing. Preset cells
take a muted hue from their name's tag so LD, PD and BS read apart at a glance.

**A drag redraws one display, not fifteen.** Each display records, while it
draws, every parameter it read; an edit redraws only the displays whose last
drawing depended on that key (`redrawViz(keys)`), and a dump, a tab change or a
resize redraws everything (`redrawViz()`). Each curve is built once into a
`Path2D` and reused by the fill and both strokes. While a finger is on a control
the trace's glow is a wide translucent stroke rather than `shadowBlur` -- the
slowest primitive the 2D context has -- and the two LFO scopes stand still; they
otherwise run at 30 fps. The knob's arc glow is a second, wider stroke, not an
SVG filter, so a value change does not re-rasterise a filtered region. Measured
by the maintainer on the first cut: a drag frame redrew every display with blur
at 0.36 ms each at dpr 2, 5.4 ms per frame, before any of this.

## Looking at it without a device

    python3 src/tools/remote_preview.py            # -> build-preview/je8086-remote-preview.html
    node tests/remote/model_test.mjs

The preview's presets and values are examples, not factory data. On a device,
open Schwung Manager, Remote UI, and the slot holding the JE-8086; the
Interface toggle there still offers the manager's generated view.

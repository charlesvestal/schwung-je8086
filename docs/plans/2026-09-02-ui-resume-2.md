## First hardware result — THE OPEN BUG

Charles loaded it in a slot and opened the editor. The screen shows a
list page:

```
JP-8000
0
#1/1
0
------
0
```

i.e. the preset browser (level `patch`: `list_param patch`, `count_param
patch_count`, `name_param patch_name`) rendered with **count = 1, index 0,
and "0" where the name and every other field should be**. Expected: Factory
A, `#1/64`, a real patch name, and a knob page behind the click.

Nothing has been diagnosed yet. Leads, in the order to check:

1. **Was the new dsp.so actually loaded?** Charles says reload picks it up; the
   old on-device build (2 702 016 B, 06:48) had no hierarchy at all, so a
   hierarchy-shaped page at least suggests the new one — but confirm via
   `__status` / `chain_params` size before reasoning further. If the shadow
   UI cached the OLD contract (planner latches), a slot unload+reload or a
   Move restart settles it.
2. **`patch_count` = 1 and everything else "0"** smells like reads served
   *before* `ui_ready` / `child_ready` being turned into a picture — but the
   plugin returns -1 there, not "0" or "1". Check what the chain host does
   with a -1 from `get_param` for a synth in a slot (`modules/chain/dsp/`,
   the `synth:` prefix route): if it maps -1 to `"0"`/`"1"` or to an empty
   string that the browser then formats, that is the whole bug. Also check
   whether the browser treats a null count as 1.
3. If reads are genuine: did the child reach `child_ready`? Banks are built
   right after ROM load, before the warm-up; if `rom.getPresets` yielded
   nothing, `patch_bank_count` = 0 → `bank` enum "None" and
   `patch_count` = 0 (not 1). `patch_bank_sizes[0]` = 1 would be odd.
   `tools/bank_scan_test.cpp` and `je_snapshot.cpp` show how presets were
   enumerated on the host earlier — the ROM preset count was verified there.
4. Enable the unified logger *briefly* (`touch
   /data/UserData/schwung/debug_log_on`, then `rm` it) and reload the slot;
   look for the plugin's status strings ("Scanning banks...", `img_valid`
   log line at the end of warm-up). If the plugin only logs to stderr, use
   `__status` through the param channel instead.
5. Reproduce on the host first where possible (memory: "reproduce on the
   HOST before the device") — `tools/plugin_host_test.cpp` /
   `plugin_drive.cpp` load the plugin natively (native build dirs exist:
   `build-native-dense`). Driving `get_param("patch_count")` after boot
   there tells host-side truth from device-side truth apart.

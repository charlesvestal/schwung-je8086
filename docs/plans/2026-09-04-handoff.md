## KNOWN BUG in v0.5.0 — fix before cataloguing

Restoring state shows the last loaded performance/patch name, but the FACTORY
BANK is what is actually loaded. Reported by the user, not yet investigated.
Neighbouring notes in the module's CLAUDE.md that almost certainly bear on it:

- `state_apply` writes our image OPTIMISTICALLY and the firmware only parses the
  DT1 bytes while it steps; the boot thread waits for a temp dump back before
  setting `ui_ready`, bounded at 4 s.
- `patch_name` / `performance_name` read the PARSED BANK; `loaded_patch_name` /
  `loaded_performance_name` ask the image.

Two probes that lied about this class of bug before: `temp_refresh` forces the
child to step and so SUPPLIES the stepping whose absence is the bug, and a
spectral similarity score cannot separate "right patch, different LFO phase"
from "wrong patch" (0.86 vs 0.93 where the byte comparison read 0/528).
**Compare the bytes.**

Best done in a fresh session — it is module code, not gearmulator, and none of
the upstream context helps.

## How the PR work is organised

**Branch per PR in the submodule; notes per PR in the parent.** The PR branches
live in `libs/gearmulator` (pushed to our gearmulator fork); the findings live
in `docs/plans/pr/<name>.md` HERE. Two different repositories, so notes cannot
leak into a gearmulator PR regardless of what is committed. See
`docs/plans/pr/README.md` for the status table.

A PR branch contains ONLY what goes upstream. Check before opening:

    git diff --stat upstream-gearmulator/main..pr/<name>

## Decisions made today

**PR 1 (denormal FTZ) is DROPPED** — full reasoning in
`pr/denormal-ftz-dropped.md`. The code is genuinely dead — proven at the
preprocessor level for both arm64 and x86-64 — but it buys nothing measurable.
Counterbalanced A/B gave ~0.1%, inside the noise; the apparent 2% in the first
test was an order effect (FTZ-off always ran second while the Pi warmed 50->70
C). Without a number it is a scold, not a contribution. The premise was also
sharper than first stated: `HAVE_SSE` IS defined, in `dsp56kBase/buildconfig.h`,
but `baseLib` neither includes nor links it, so the guard is dead on EVERY
platform rather than just ARM.

**PR 2 (the MIDI printf) is not a performance fix** and should not be pitched as
one. `printf` line-buffers only on a tty; redirected it is one syscall per ~230
calls, and `0xFE` active sensing — the only frequent MIDI out — is already
excluded. The real argument is that a library should not own stdout, which is
how it bit us: our Move module reads parameter data on that stream.

**Lead with PR 6, not PR 1 or 2** -- but NOT for the reason first written here.
"The largest single engine win" is now retracted twice over: PR 6 measured +6%,
and PR 9 (dense ARM64 emitter) measured **+65% on A72 and +45% on M1, bit-exact
over 378.7 s**. PR 6 still goes first because it is small, self-contained and an
easy yes that establishes the measurement methodology -- then PR 9 straight
after, referencing it.

**x86 is disclosed, not measured.** No hardware; CI is noisy and `bench_je`
needs the copyrighted ROMs (635 KB against a 64 KB secret limit). Wording is in
the companion doc. Do NOT use Docker x86_64 on Apple Silicon — that is
translation and its timings mean nothing.

**Multicore DSP stays behind "Enable Advanced Options."** Neither that checkbox
nor its instability warning is ours — both predate us in `settings.cpp` and the
same rml. Argue placement in the PR.

## Measuring against upstream — READ THIS BEFORE TRYING

**`bench_je` does NOT build on an upstream base.** `dsp_bench.cpp` references
`g_je_uc_read_capture`, `g_je_uc_write_capture` and `g_je_audio_tap`, all of
which are our additions to `je8086devices.h`. It needs no snapshots, but it does
need our instrumentation.

**Use `jeTestConsole` — upstream's own tool — and it is better than ours for
this.** It self-triggers: waits for LCD `PERFORM`, presses Rec+Hold itself,
waits for `=== ROM PLAY ===`, then records `je8086_out.wav` and prints
`Recorded N sec, last interval speed X%` once per rendered second. Crucially
`t0` starts AFTER the demo begins, so **boot is excluded by construction** — the
trap that produced several retracted numbers here.

Two gotchas: it finds ROMs via CWD (copy the eight `.mid` files into the run
directory; the path argument is ignored), and boot takes ~60-90 s on a Pi before
anything is reported, so a 75 s timeout sees nothing and looks like a hang.

Build it with `ninja JE8086TestConsole` in `build-plugin` — NOT in `build`,
which only configures our own targets.

## Method, learned the hard way

- Benchmark on an IDLE box; check `/proc/loadavg` first.
- **Counterbalance the order** (B,A,A,B), do not just alternate. Straight
  alternation plus thermal drift manufactured a 2% result that did not survive.
- Check `vcgencmd get_throttled` and temperature before AND after.
- `ps` %CPU is a lifetime average and folds boot in forever; use
  `/proc/<tid>/stat` deltas.
- A72 hardware, not a dev Mac.

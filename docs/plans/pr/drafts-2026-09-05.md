## New PR: pr/esp-arm64-jit-entry-state

**Title:** esp: ARM64 JIT must load and store the ESP's persistent state, not
inherit registers

**Body:**

The ESP's ERAM latch chain (`eramReadLatch`, `eramWriteLatch/Next`,
`eramVarOffset`, `eramEffectiveAddr`), the DMAC inputs (`last_mulInputA/B_24`)
and the six accumulators persist across samples: the interpreter keeps them in
the ESP object, and the x64 backend loads and stores them through the
`JitInputData` pointers. The ARM64 backend kept them purely in registers and
never initialised them — on entry to the generated program each held whatever
the calling code happened to leave in that register.

With a fixed calling sequence that garbage is reproducible, which is why this
never showed: one binary's output is stable run to run. But it is an accident
of code generation. Three builds of the same source (different incidental code
around `callOptimized`) each produce different audio from the factory demo's
patch change to `5:Feedbacker` at ~176 s — a stray ERAM write during boot that
surfaces there as ~-115 dB noise for a second or two. Anything that changes
the caller changes the output: another compiler, an unrelated PR in the tree,
or running an ASIC from a worker thread.

This fix loads the persistent state in `jitEnter` and writes it back in
`jitExit`, matching the x64 backend's contract; registers with no backing
state are zeroed so entry state is deterministic. Cost is ~30 instructions per
call, i.e. once per 384 emulated ESP steps — not measurable in the render
benches here.

After this change, the ARM64 backend's output is **byte-identical to the x64
backend's** over a 200 s demo render (fat binary on an M1, x64 slice under
Rosetta) — before it, the two differ at 176 s. It also makes the demo render
invariant across builds, threads and compilers on arm64 (verified 200 s on
M1/clang, 380 s on a Pi 4/gcc).

This is also the cause of the divergence I reported against #293 — see the
correction there.

## Correction comment for #293

Retracting my "not bit-exact" correction: the 176.0 s divergence is not this
PR, and the timer logic was never wrong.

The cause is #<fixpr>: the ARM64 JIT enters its generated programs with
uninitialised registers (the ERAM latch chain among them), so the audio at the
demo's 176 s patch change depends on incidental binary layout. ANY change to
the tree shifts it — this branch merely produced a different binary. Three
builds of unmodified main disagree with each other at the same spot, and the
arm64 backend disagrees with the x64 backend there too.

The tick()/catchUp() asymmetry I said I was chasing is innocent — the timer
event and IRQ streams were already measured identical between this branch and
main while the audio differed, which is exactly the fingerprint of the JIT
bug rather than a timing change.

With #<fixpr> applied to both sides, this branch is byte-identical to main
over 380 s on a Pi 4 (gcc) and 200 s on an M1 (clang), through the 176 s
patch change. Once #<fixpr> is in, I'll take this out of draft.

## #297 — comment resolving the 176 s qualification

The 176 s qualification in the description is resolved, and the answer is
better than I hoped: nothing in this branch or in the emitter branch is wrong.
The cause is #<fixpr> — the ARM64 JIT enters its generated programs with
uninitialised registers, so its output depends on WHO CALLS IT. Running ASICs
from stage threads changes the caller; so does merely building a different
binary, which is why the "interaction" pointed at the emitter. The mirrored-
ring lead I described was wrong: traces show the GRAM handoffs, forwarded
register writes and recompile ticks all byte-identical between serial and
pipeline — the stray write was one uninitialised ERAM latch during boot,
surfacing 172 s later.

With #<fixpr> in the tree, the full stack (this branch + the emitter + the
H8S changes) renders byte-identical to serial at 2, 3 and 4 stages over 380 s
on a Pi 4 and 200 s on an M1, through the 176 s patch change. So the delivery
contract holds unqualified once that fix is present; I'll rebase the claim on
it when it lands.
